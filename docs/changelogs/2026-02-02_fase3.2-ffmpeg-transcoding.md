### 2. Implementação FFmpeg

**Características**:
- Geração de comando FFmpeg complexo com múltiplas variantes de qualidade
- Suporte a hardware acceleration (configurável)
- HLS output com segmentos de 6 segundos
- Master playlist com adaptive bitrate (ABR)
- Filter complex para scaling simultâneo de múltiplas resoluções

**Presets de Qualidade**:
| Nome | Resolução | Bitrate Vídeo | Bitrate Áudio | Preset |
|------|-----------|---------------|---------------|--------|
| 1080p | 1920x1080 | 5000 kbps | 128 kbps | medium |
| 720p | 1280x720 | 2800 kbps | 128 kbps | medium |
| 480p | 854x480 | 1400 kbps | 128 kbps | fast |
| 360p | 640x360 | 800 kbps | 96 kbps | faster |

**Comando FFmpeg gerado** (exemplo):
```bash
ffmpeg -i rtmp://localhost:1935/live/stream_key \
  -filter_complex "[v:0]split=4[v0][v1][v2][v3]; \
    [v0]scale=w=1920:h=1080[v0out]; \
    [v1]scale=w=1280:h=720[v1out]; \
    [v2]scale=w=854:h=480[v2out]; \
    [v3]scale=w=640:h=360[v3out]" \
  -map "[v0out]" -c:v:0 libx264 -b:v:0 5000k -preset medium \
  -map "[v1out]" -c:v:1 libx264 -b:v:1 2800k -preset medium \
  -map "[v2out]" -c:v:2 libx264 -b:v:2 1400k -preset fast \
  -map "[v3out]" -c:v:3 libx264 -b:v:3 800k -preset faster \
  -f hls -hls_time 6 -master_pl_name master.m3u8 \
  -hls_segment_filename "/tmp/hls/stream_key/v%v/segment_%03d.ts" \
  "/tmp/hls/stream_key/v%v/playlist.m3u8"
```

### 3. Script de Transcodificação

**Arquivo criado**: `docker/nginx-rtmp/transcode.sh`

**Funcionalidades**:
- Script shell executado pelo Nginx-RTMP via `exec_push`
- Recebe stream key e URL RTMP como parâmetros
- Cria diretórios de output automaticamente
- Logging de transcodificação em arquivo

**Estrutura de output**:

### 4. Integração Nginx-RTMP

**Alterações em `nginx.conf`**:
```nginx
application live {
    live on;
    record off;
    
    # HTTP callbacks
    on_publish http://streaming-platform:8080/api/streams/callback/publish;
    on_publish_done http://streaming-platform:8080/api/streams/callback/publish_done;
    on_done http://streaming-platform:8080/api/streams/callback/done;
    
    # Execute FFmpeg transcoding when stream starts
    exec_push /usr/local/bin/transcode.sh $name rtmp://localhost:1935/live/$name;
    
    # HLS configuration
    hls on;
    hls_path /tmp/hls;
    hls_fragment 6s;
    hls_playlist_length 60s;
    hls_nested on;
    hls_cleanup on;
    
    deny play all;
}
```

## Fluxo de Transcodificação

```
1. OBS → RTMP → Nginx-RTMP (porta 1935)
2. Nginx valida stream key via callback HTTP
3. on_publish_done → exec_push transcode.sh
4. FFmpeg inicia transcodificação:
   - Lê stream RTMP
   - Aplica filter complex (scaling)
   - Gera 4 variantes de qualidade
   - Output HLS segmentado
5. Arquivos HLS salvos em /tmp/hls/{stream_key}/
6. Nginx HLS serve arquivos (porta 8081)
7. Player HLS consome master.m3u8 com ABR
```

## Decisões Técnicas

### Por que Abstração com Gateway?
- Permite comparação de tecnologias (objetivo do TCC)
- Trocar FFmpeg para GStreamer requer apenas:
  1. Criar `GStreamerTranscoderGateway implements TranscoderGateway`
  2. Alterar `streaming.transcoding.provider=gstreamer`
- Zero impacto no código de negócio

### Por que 4 Qualidades?
- **1080p**: Full HD para conexões rápidas
- **720p**: HD padrão (sweet spot qualidade/tamanho)
- **480p**: SD para conexões médias
- **360p**: Baixa qualidade para conexões lentas
- Permite ABR efetivo cobrindo ampla gama de conexões

### Por que exec_push no Nginx?
- Inicia transcodificação automaticamente quando stream começa
- Processo filho do Nginx (gerenciamento automático)
- Logs centralizados
- Kill automático quando stream encerra

### Por que Presets Diferentes por Qualidade?
- **1080p/720p**: `medium` - máxima qualidade, consome mais CPU
- **480p**: `fast` - balanceamento qualidade/performance
- **360p**: `faster` - prioriza velocidade sobre qualidade
- Otimiza uso de recursos sem comprometer experiência

## Observações

### Performance
- Transcodificação 4 qualidades consome ~300-400% CPU por stream
- Recomendado máx. 2-3 streams simultâneas em desenvolvimento
- Produção: considerar GPU acceleration ou servidores dedicados

### Limitações Atuais
- HLS latency: 18-36 segundos (3-6 segmentos)
- Sem suporte a LL-HLS (Low Latency HLS) ainda
- Hardware acceleration desabilitado por padrão

### Melhorias Futuras
- Implementar LL-HLS para latência < 10s
- Adicionar support para VP9/AV1 codecs
- Implementar dynamic quality adjustment baseado em CPU load
