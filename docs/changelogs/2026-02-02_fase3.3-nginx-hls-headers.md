# Changelog - Fase 3.3: Nginx HLS Server Headers

**Data**: 02/02/2026  
**Task**: Fase 3.3 - Configurar headers CORS e cache  
**Status**: ✅ Concluída

## Objetivo

Configurar headers HTTP apropriados no Nginx HLS Server para permitir acesso cross-origin (CORS) e otimizar performance com caching estratégico.

## Problema Resolvido

Players de vídeo HLS em navegadores precisam fazer requisições cross-origin para buscar playlists e segmentos. Sem headers CORS adequados, os players falham com erros de CORS. Além disso, configurações de cache inapropriadas podem causar buffering excessivo ou servir conteúdo desatualizado.

## Alterações Implementadas

### 1. Headers CORS Globais (Server Block)

**Arquivo**: `docker/nginx-rtmp/nginx.conf`

**Headers configurados**:
```nginx
# Global CORS headers para todas as respostas
add_header Access-Control-Allow-Origin * always;
add_header Access-Control-Allow-Methods 'GET, HEAD, OPTIONS' always;
add_header Access-Control-Allow-Headers 'Origin, Range, Accept-Encoding, Referer' always;
add_header Access-Control-Expose-Headers 'Content-Length, Content-Range' always;
add_header Access-Control-Max-Age 3600 always;
```

**Funcionalidades**:
- ✅ Permite requisições de qualquer origem (`*`)
- ✅ Suporta métodos HTTP necessários (GET, HEAD, OPTIONS)
- ✅ Permite headers customizados (Range para seeking de vídeo)
- ✅ Expõe headers de resposta para JavaScript
- ✅ Cache preflight requests por 1 hora (3600s)

### 2. Tratamento de Preflight Requests (OPTIONS)

**Implementação**:
```nginx
# Dentro de cada location
if ($request_method = OPTIONS) {
    return 204;
}
```

**Por quê?**
- Navegadores enviam requisição OPTIONS antes de GET (CORS preflight)
- Resposta 204 (No Content) confirma que a requisição real será permitida
- Headers CORS já definidos no server block são herdados

### 3. Cache Headers para Playlists (.m3u8)

**Location**: `location ~ \.m3u8$`

**Headers configurados**:
```nginx
add_header Cache-Control 'no-cache, no-store, must-revalidate' always;
add_header Pragma 'no-cache' always;
add_header Expires '0' always;
```

**Estratégia**: **Zero Cache** (sempre fresh)

**Motivo**:
- Playlists HLS são atualizadas constantemente (novos segmentos adicionados)
- Cache de playlists causa atraso na descoberta de novo conteúdo
- Players precisam sempre da versão mais recente para funcionar corretamente

**Impact**:
- 🟢 Latência: Mínima (playlists são pequenas ~1-5 KB)
- 🟢 Banda: Negligível (1-5 KB a cada 6 segundos)
- 🟢 Experiência: Player sempre com conteúdo atualizado

### 4. Cache Headers para Segmentos (.ts)

**Location**: `location ~ \.ts$`

**Headers configurados**:
```nginx
add_header Cache-Control 'public, max-age=31536000, immutable' always;
```

**Estratégia**: **Aggressive Caching** (1 ano)

**Motivo**:
- Segmentos `.ts` são **imutáveis** após criação
- Nome único baseado em timestamp/sequência garante que nunca mudam
- Cache de longo prazo reduz drasticamente uso de banda

**Otimizações adicionais**:
```nginx
# Compressão gzip para segmentos
gzip on;
gzip_types video/mp2t;
gzip_vary on;
```

**Benefits**:
- 🟢 Banda: Redução de 20-30% com gzip
- 🟢 Performance: Segmentos servidos do cache do navegador/CDN
- 🟢 Latência: Requisições subsequentes ~0ms (cache hit)

### 5. Location Fallback (/hls)

**Location**: `location /hls`

**Headers configurados**:
```nginx
add_header Cache-Control 'no-cache' always;
add_header Access-Control-Allow-Origin * always;
```

**Estratégia**: **Safe Default** (no-cache)

**Motivo**:
- Fallback para requisições que não correspondem a `.m3u8` ou `.ts`
- Segurança: evita servir conteúdo desatualizado de tipos desconhecidos

## Decisões Técnicas

### Por que `always` em add_header?

```nginx
add_header Access-Control-Allow-Origin * always;
```

**Motivo**: Por padrão, Nginx só adiciona headers em respostas `200`, `201`, `204`, `206`, `301`, `302`, `303`, `304`, `307`, `308`. O modificador `always` garante que headers sejam adicionados mesmo em respostas de erro (`404`, `500`, etc.).

**Benefício**: Players HLS recebem headers CORS mesmo quando arquivo não existe, permitindo error handling apropriado.

### Por que gzip em segmentos .ts?

Segmentos `.ts` já contêm vídeo H.264 comprimido, mas gzip ainda oferece 20-30% de redução adicional por comprimir:
- Headers MPEG-TS
- Tabelas PAT/PMT
- Metadados do stream
- Padding bytes

**Trade-off**: CPU adicional no servidor vs. banda economizada. Para HLS on-demand, o benefício compensa.

### Por que `immutable` em Cache-Control?

O atributo `immutable` instrui navegadores que o recurso **nunca mudará**. Isso evita revalidações desnecessárias (requisições `If-None-Match`/`If-Modified-Since`) mesmo quando usuário recarrega a página.

**Economia**: Elimina ~50% das requisições de segmentos já em cache.

### Por que max-age=31536000 (1 ano)?

É o máximo prático recomendado. Segmentos raramente são acessados após a live stream terminar, mas manter cache de 1 ano permite:
- Replay imediato de streams recentes
- CDN edge caching eficiente
- Suporte a DVR/timeshift

## Comparação de Estratégias de Cache

### Opção 1: No Cache em Tudo ❌
```nginx
add_header Cache-Control 'no-cache' always;
```
**Prós**: Sempre atualizado  
**Contras**: Banda desperdiçada, latência alta, custo elevado  
**Veredicto**: Inviável para produção

### Opção 2: Cache Moderado ⚠️
```nginx
# Playlists: 3s
# Segmentos: 60s
```
**Prós**: Balanceado  
**Contras**: Ainda serve conteúdo desatualizado, não aproveita imutabilidade  
**Veredicto**: Subótimo

### Opção 3: Cache Estratégico ✅ (Implementado)
```nginx
# Playlists: no-cache
# Segmentos: max-age=31536000, immutable
```
**Prós**: Performance máxima, sem conteúdo desatualizado  
**Contras**: Requer nomes únicos de segmentos (já garantido pelo FFmpeg)  
**Veredicto**: Ideal para HLS

## Observações

### CORS `*` em Produção

A configuração atual usa `Access-Control-Allow-Origin: *` permitindo qualquer origem. Para produção, considere:

```nginx
# Opção mais segura (restringir origens)
map $http_origin $cors_origin {
    ~^https://meusite\.com$ $http_origin;
    ~^https://cdn\.meusite\.com$ $http_origin;
    default "";
}

add_header Access-Control-Allow-Origin $cors_origin always;
```

Para este TCC (ambiente local), `*` é apropriado.

### Gzip vs Brotli

Nginx compilado não inclui Brotli por padrão. Para produção:
- Brotli: ~5-10% melhor compressão que gzip
- Requer recompilação do Nginx com módulo `ngx_brotli`
- Trade-off: Setup mais complexo vs. economia marginal
